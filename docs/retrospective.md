# 振り返り（模擬案件）

次の案件に活かすための振り返りです。コミット履歴・コード・ドキュメントから確認できた事実をもとにしています。

---

## 1. 案件概要

- **内容**: 美容室向けの LINE 問い合わせ Bot と、スマートフォン向け管理画面
- **想定クライアント**: 個人経営の美容室オーナー（非エンジニア、管理者1名）
- **課題**: 営業時間・料金・駐車場などの定型的な問い合わせへの返信負担を減らしつつ、AI の誤回答でお客様に間違った案内をしないこと
- **期間**: 2026-09-13（初期コミット）〜 2026-09-28（本番デプロイ）

## 2. 実装したもの

| フェーズ | 内容 |
|---|---|
| Phase 1 基盤構築 | LINE Webhook、署名検証、会話ログ（Supabase）、再送メッセージの二重処理防止 |
| Phase 2 FAQ 自動回答 | Claude による FAQ ベースの回答、確信度（high/medium/low）判定、根拠 FAQ の実在検証、低確信度時のオーナー通知 |
| Phase 3 管理画面 | パスワード認証、FAQ・メニュー管理、会話ログ閲覧、お知らせ一斉配信（二重配信防止付き） |

最終的に 37ファイル / 593テスト、Vercel 本番稼働。

---

## 3. うまくいったこと

- **段階的な実装**: Phase → Step に分け、各 Step で「実装 → テスト → コードレビュー → 報告して停止」を守った。DB マイグレーションはユーザーが SQL を実行して確認するまで次に進まなかった。
- **AI を無条件に信用しない設計**: Claude の `confidence` と `matchedFaqIds` を自己申告として扱い、実在しない FAQ ID を除外、根拠0件なら強制的にスタッフ確認へ回した。低確信度時は AI の回答文をお客様に送らない。
- **二重配信防止の多層化**: 条件付き UPDATE、LINE の retry key、23時間の送信期限、「結果不明なら自動再送しない」を組み合わせた。
- **実送信を伴わない検証**: LINE・Supabase・Claude をすべてモックし、0003 の CHECK 制約を再現したインメモリ DB で配信ロジックをテストした。実 Broadcast は一度も実行していない。
- **秘密情報の管理**: 公開リポジトリ前提で、ビルド成果物（`.next/static`）と Git 履歴に環境変数名・値が含まれないことを確認した。クライアントバンドルから Zod（約392KB）も除外した。
- **非エンジニア向け UI**: 専門用語を避けた日本語表示、ボタンの押下中表示と二重送信防止、削除・一斉配信の確認ダイアログ、最後の公開 FAQ を消す前の警告。

## 4. 苦戦したこと

- **Webhook の再送と重複処理**: 一意制約で重複を検知する方式にしたが、処理失敗時に受信ログが残ると正当な再送まで弾いてしまう問題があり、補償削除を追加した。それでも「1回目の処理中に届いた再送」は防ぎきれず、既知のリスクとして受け入れた。
- **FAQ / メニューと Bot の役割整理**: メニュー・料金は Bot に連携しない（Claude に渡すのは FAQ のみ）と決めた。誤解されやすいため、管理画面とマニュアルで繰り返し明記する必要があった。
- **お知らせの二重配信対策**: 「送信中にサーバーが止まったら？」「retry key が24時間で切れたら？」を詰め、送信期限を23時間にし、409 を成功扱いにする設計に落ち着いた。
- **`sending` のまま止まった場合の方針**: 自動復旧は二重配信の危険があるため行わず、10分で「状態確認が必要」と表示して人が確認する方針にした。閾値は当初30分だったが、Server Action の `maxDuration`（60秒）を明示したうえで10分に見直した。復旧 UI は未実装（SQL で対応）。
- **管理画面の認証**: `proxy.ts` だけでは Server Action を守れない（Action ID で呼ばれるため）ことを踏まえ、全ページ・Server Action・データ関数で `requireAdmin()` を呼び、テストで強制した。レビューで一部ページの呼び出し漏れが見つかり修正した。
- **フレームワークの挙動**: Server Action の `redirect()` でページの部品が作り直され、入力途中のお知らせ本文が消える問題があった。モジュールレベルのストア（`useSyncExternalStore`）で解決した。
- **開発環境**: OneDrive 配下で `.next` が読み取り専用になり、ビルドが `EPERM` で失敗することがあった。
- **ドキュメントの正確性**: 自動生成したドキュメントに、実装に無い機能（ドラッグ&ドロップでの並び替え、下書き削除など）が書かれていた。コードと突き合わせて修正する必要があった。
- **進捗報告の取り違え**: Step 8 の依頼に Step 7 の報告が返ったことがあり、完了状況を記録とコードで確認し直した。

## 5. 学んだこと

- **要件確認**: 「メニューを Bot に使うか」「送信枠の上限」「管理者は何人か」など、運用の前提で設計が大きく変わる。最初に確認すべきだった。
- **段階実装**: 1 Step ごとに止まって確認することで、DB 変更や外部送信といった取り返しのつかない操作を安全に進められた。
- **セキュリティ**: 「AI の出力」「Webhook の入力」「URL パラメータ」はすべて信用しない入力として扱う。認証は入口（proxy）ではなく、処理の直前で確認する。
- **テスト**: 外部サービスはモックし、DB 制約を再現したフェイクで状態遷移を検証すると、実送信なしで安全性を確かめられる。
- **デプロイ**: GitHub 連携の Vercel では push がそのまま本番デプロイになる。環境変数の登録範囲（Production のみ）まで含めて手順化が必要。
- **納品ドキュメント**: 動くものを渡すだけでは運用できない。オーナー向けと開発者向けを分け、実装と一致しているかを確認する工程が要る。

## 6. 次回改善すること

- **運用要件を最初に明確化する**: 管理者の人数、LINE の料金プランと送信枠、メニューを Bot に使うか、会話ログの保存期間を着手前に決める。
- **本番環境と開発環境を分ける**: 今回は開発・手動テストと本番で同じ Supabase・同じ LINE チャネルを使ったため、テストデータの整理が必要になった。環境ごとにプロジェクト・チャネルを分ける。
- **レート制限を最初から入れる**: Webhook の顧客別制限とログイン試行回数の制限を、アプリ側（または WAF 設定込み）で設計に含める。
- **テストデータを管理する**: テストデータに目印を付ける、または専用環境でだけ作る。
- **ドキュメントを実装と同時に更新する**: 各 Step の完了条件にドキュメント更新と実装との突き合わせを含める。
- **運用で必要な操作を UI に用意する**: `sending` の復旧、下書きの削除・編集など、今回 SQL に頼った操作を検討する。
- **公開ページを早めに用意する**: 公開 URL の `/` が納品準備の段階まで Next.js の初期ページのままだった。最初のデプロイ時に紹介ページを置く。

## 7. ポートフォリオで伝えるポイント

- **LINE Messaging API**: Webhook の署名検証、Reply / Push / Broadcast の使い分け、retry key による冪等な一斉配信
- **Claude API**: 構造化出力（Zod スキーマ）、確信度判定、根拠 FAQ の実在検証、プロンプトインジェクション対策、タイムアウトと障害時の定型文
- **Supabase**: RLS 全拒否 + サーバー側のみ service role、CHECK 制約で状態の整合性を保証、一意制約による重複処理防止
- **Next.js（App Router）**: Server Components / Server Actions 中心の構成、Client Component を最小限にしてバンドルから重い依存を除外
- **管理画面**: 非エンジニアが迷わないスマホファースト UI、危険な操作の確認ダイアログ
- **認証**: パスワード + HMAC 署名付き Cookie、多層防御（proxy + `requireAdmin()` + テストによる強制）
- **本番デプロイ**: Vercel、環境変数を Production のみに限定、公開リポジトリでの秘密情報管理
- **テスト**: 593件のテスト、外部サービスのモック、結合テスト、セキュリティ要件のテスト化
- **実運用を想定した設計**: 送信枠の消費を意識した通知設計、二重配信の防止、結果不明時に自動再送しない判断、運用マニュアルと引き継ぎ資料
